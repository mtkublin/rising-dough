# ADR-0080: v4 Envelope Encryption — Key Hierarchy, Server Secrets, Session Binding

- **Status**: Proposed
- **Date**: 2026-11-04
- **Amends**: [ADR-0067](0067-auth-backend-sessions-and-passkey-challenges.md) (session rows carry a wrapped key; login yields keys), [ADR-0070](0070-auth-web-layer-cookies-middleware-order.md) §2 (session cookie value format), ADR-0076 (session hardening, in flight on `wi/v3/T-D53`; id rotation re-wraps the key), [ADR-0019](0019-soft-delete-and-audit-log.md) (key-wrap rows are hard-deleted; see §2)
- **Related**: [ADR-0079](0079-v4-threat-model-and-data-protection-goals.md), [ADR-0081](0081-v4-field-level-encryption-scope-and-query-model.md), [ADR-0082](0082-v4-account-lifecycle-recovery-and-migration.md), [ADR-0072](0072-auth-rate-limit-sqlite-fixed-window.md)

## Context

ADR-0079 chose per-user envelope encryption, with keys wrapped by user-held secrets and unwrapped only during a session. This ADR fixes the cryptographic construction, where server-side secrets live, and how a session holds a key without the server storing it in usable form.

## Decision

### 1. Primitives

| Purpose | Primitive | Library |
|---|---|---|
| Field and key encryption | AES-256-GCM, 96-bit random nonce, 128-bit tag | `cryptography` (`AESGCM`) — already a dependency |
| Password stretching | Argon2id, `m = 64 MiB`, `t = 3`, `p = 1`, 32-byte output (params stored per wrap for future tuning) | **`argon2-cffi`** (new; `argon2.low_level.hash_secret_raw`) |
| Key derivation and separation | HKDF-SHA256 | `cryptography` |
| Blind indexes | HMAC-SHA256, truncated to 16 bytes | stdlib `hmac` |
| Randomness | `secrets.token_bytes` | stdlib |

No custom primitives. Nonce reuse is negligible at our volume (well under 2³² encryptions per key). Library calls go through one module, `src/budget_planner/crypto/`, made of pure functions (ADR-0021); nothing else imports `cryptography` directly. A static test enforces this.

### 2. Key hierarchy

```
 credential secrets (user-held)            server secrets (Secret Manager)
 ├─ password ──Argon2id──┐                 ├─ PEPPER
 ├─ passkey PRF output ──┤                 └─ ESCROW_MASTER (transitional, ADR-0082 §2)
 ├─ recovery code ───────┤
 └─ (escrow) ────────────┤
                         ▼
            KEK_<kind>  (HKDF, one per credential; never stored)
                         │  wraps
                         ▼
            UMK  — user master key, 256-bit random, one per user, stable
                         │  wraps (versioned)
                         ▼
            DEK_v — data key, version v; HKDF subkeys:
                   K_enc  (info "bp/dek/enc/v1")   → field encryption
                   K_bidx (info "bp/dek/bidx/v1")  → blind indexes
```

- **KEK derivations**:
  - `KEK_password = HKDF(ikm=Argon2id(password, salt), salt=PEPPER, info="bp/kek/password/v1")`
  - `KEK_prf = HKDF(ikm=PRF_output, salt=credential_id, info="bp/kek/prf/v1")`
  - `KEK_recovery = HKDF(ikm=recovery_code_bytes, salt=salt, info="bp/kek/recovery/v1")`. The recovery code is 128-bit random, so it needs no Argon2.
  - `KEK_escrow = HKDF(ikm=ESCROW_MASTER, salt=user_id, info="bp/kek/escrow/v1")`
- The password used for login verification (bcrypt, ADR-0067) is unchanged and has its own salt. Argon2id is used only for the key-encryption key. The two outputs are unrelated.
- **Why two levels (UMK → DEK).** Rotating the data key, after suspected exposure or on a schedule, must not require the user's credentials. A live session holds the UMK. It can mint `DEK_{v+1}`, re-encrypt the user's rows and retire `DEK_v` without touching any credential wrap. Rotating the UMK itself means re-enrolling credentials: the "reset all credentials" flow in ADR-0082 §6.
- **Storage.** A new table `user_key_wraps` holds both layers:

  | column | meaning |
  |---|---|
  | `id`, `user_id` | owner |
  | `layer` | `umk` (credential → UMK) or `dek` (UMK → DEK_v) |
  | `kind` | for `umk`: `password` \| `passkey_prf` \| `recovery` \| `escrow`; for `dek`: `data` |
  | `credential_ref` | webauthn credential id (for `passkey_prf`); NULL otherwise |
  | `key_version` | DEK version (`dek` rows); pepper version (`password` rows) |
  | `kdf_params` | JSON (Argon2 params, salt) |
  | `wrapped` | `AES-GCM(KEK or UMK, key, aad="bp/wrap/v1\|u:<user_id>\|<layer>:<kind>:<version>")` |
  | `created_at`, `last_used_at` | — |

  **Exception to ADR-0019.** Wrap rows are **hard-deleted**, with `secure_delete` on (ADR-0078 §6). A soft-deleted wrap would defeat revocation and crypto-shredding. Every insert and delete writes a metadata-only audit row (`entity_type='key_wrap'`, no key bytes).

### 3. Server-side secrets

- `PEPPER` and `ESCROW_MASTER` are each 32 random bytes, generated by an operator CLI (`python -m budget_planner.cli.secrets generate`).
- They're stored in **Scaleway Secret Manager**. Terraform manages only the secret containers and a read-only IAM application scoped to them. Secret **versions** are uploaded by the operator CLI, so the values never enter Terraform state. The app fetches them at startup and holds them only in memory. Copies go in the operator password manager.
- **Fallback.** If Secret Manager is unavailable in `pl-waw` (verified in task T-E03), use a cloud-init file at `0600` (the v3 secret path, ADR-0069). That puts the values in Terraform state; the trade-off is recorded in the task handoff.
- Production refuses to start without both secrets, like `cookie_secret` (T-D03). Dev and test use deterministic per-environment values from settings.
- **Pepper rotation.** `password` wraps record `pepper_version`. On the next password unlock the wrap is re-made under the new pepper. The old pepper is kept until every live wrap has migrated or 90 days pass. After that, remaining users unlock with a passkey or recovery code and are re-wrapped.
- **Pepper loss** breaks password unlock only. Users fall back to passkey PRF or recovery code and are re-wrapped. **ESCROW_MASTER loss** loses unclaimed users' data, which is why ADR-0082 bounds the escrow window.

### 4. Session binding — the key never rests on the server in usable form

- On successful unlock (login with password, PRF passkey or recovery code), the server:
  1. derives the KEK and unwraps the UMK;
  2. generates a 256-bit **session wrapping key (SWK)**;
  3. stores `sessions.wrapped_umk = AES-GCM(SWK, UMK, aad="bp/session/v1|<session_id_hash>")`;
  4. sets the session cookie to `<session_id>.<swk>` (both base64url, 256-bit). The DB stores only `sha256(session_id)` (ADR-0076 §3). **The SWK exists only in the cookie.**
- **Each request**: middleware resolves the session, unwraps the UMK with the cookie's SWK, then unwraps the current DEK into a request-scoped, immutable `UserKeys` value (`frozen=True` dataclass with `user_id`, `dek_version`, `k_enc`, `k_bidx`, plus read-only access to older DEK versions for lazy re-encryption). A FastAPI dependency `current_keys` hands it to routers, and routers pass it explicitly to services. There is no global key state. The reference is dropped when the request ends.
- **Locked sessions.** A login that yields no key leaves `wrapped_umk = NULL`, for example a passkey without PRF support. The session is authenticated but **locked**. Routes that touch user data answer the way ADR-0070 §4 does: `303 → /auth/unlock?next=…`; HTMX gets `HX-Redirect`; JSON gets `403 {"error":"unlock_required"}`. `/auth/unlock` accepts the password or a recovery code. While locked, the user can still reach `/auth/*`, `/settings/security` (read-only list), logout, `/health` and `/ready`.
- **Revocation and expiry** delete the session row, which destroys `wrapped_umk`. A stolen cookie for a revoked session decrypts nothing.
- **Session id rotation** (ADR-0076 §4, step-up) generates a new id and SWK and re-wraps the UMK under it.
- The cookie stays `HttpOnly; Secure; SameSite=Lax; __Host-`, so the SWK is unreadable to JavaScript. CSP nonces (ADR-0036) remain the XSS control.

### 5. Ciphertext envelope

- Field value layout: `0x01 ‖ dek_version (u16 BE) ‖ nonce (12 B) ‖ ciphertext ‖ tag (16 B)`, stored as `BLOB`.
- AAD = `"bp/f/v1|<table>.<column>|u:<user_id>"`. This binds a ciphertext to its column and owner, so a value can't be copied into another user's row or into another column undetected. Swapping values between two rows of the **same** user and column needs DB write access, which is the A4 class (ADR-0079 residuals) and isn't defended.
- Plaintext encodings: text → UTF-8, padded per ADR-0081 §4; integer minor units → signed int64 BE (covers the ADR-0008 reconciliation sign exception); structured → canonical JSON UTF-8.
- Decryption failure raises a typed `DecryptionError`. It's never swallowed (common error-handling rule), it's logged with table, column and row id only, and the user gets a generic error page.

### 6. Blind indexes

- `bidx = HMAC-SHA256(K_bidx, normalize(value))[:16]`, where `normalize` is NFKC, casefold and strip.
- Used only where uniqueness or equality must stay in SQL: account name and category name per user (ADR-0081 §2). The key is per user, so equal names never correlate across users.

### 7. Data-key rotation

- `rotate_data_key(conn, keys)` runs in a live session: mint `DEK_{v+1}`, wrap it under the UMK, re-encrypt every encrypted field of the user in one transaction (per-user volume is small), delete the `DEK_v` wrap, and audit it.
- Lazy mode is also supported. Reads accept any version the session holds, and writes always use the newest.
- Triggers: manual (Settings → Security, step-up guarded) and after any incident affecting that user. No scheduled rotation in v4.

### 8. Host and memory hygiene

- Container: `RLIMIT_CORE = 0` (entrypoint `ulimit -c 0`), and the process marks itself non-dumpable (`prctl(PR_SET_DUMPABLE, 0)` via ctypes, best effort, logged when unsupported).
- Host: no swap, or encrypted swap. cloud-init asserts this and T-E03 records it.
- Keys are never logged. The ADR-0078 §5 redaction processor gains the key names `umk`, `dek`, `kek`, `swk`, `k_enc`, `k_bidx`, `wrapped*`. A test sweeps captured logs for key-sized base64 runs.
- Python `bytes` can't be reliably zeroized. That's accepted and documented. Request-scoped lifetime is the mitigation.

### 9. Rate limits and resource limits

- `/auth/unlock` is rate-limited under scope `unlock` (ADR-0072 limiter): per user 5/min and 20/h, per IP 30/h.
- At most 2 concurrent Argon2id derivations (process-wide semaphore; 2 × 64 MiB) so login bursts can't exhaust memory on Stardust1-S. A request that waits more than 5 s gets `503 Retry-After: 2`.

### 10. Audit

These events are written as metadata-only audit rows (`entity_type='auth_event'`): `key_unlock` (with method), `key_unlock_failed`, `key_wrap_added`, `key_wrap_removed`, `dek_rotated`, `escrow_claimed`, `credentials_reset`. They never carry key material, salts or wrapped bytes.

## Consequences

- An attacker holding the DB, the backups and both server secrets still needs a user's password (and pays Argon2id cost per guess), a PRF passkey or a recovery code. With the DB but without `PEPPER`, offline password guessing isn't possible at all.
- Every authenticated request costs two AES-GCM unwraps (microseconds).
- Services gain an explicit `keys: UserKeys` parameter wherever they read or write encrypted fields. It's a mechanical sweep, guarded by a static check (ADR-0081 §6).
- The session cookie value grows from 43 to about 87 characters.

## Alternatives considered

- **UDK wrapped directly by credentials (one level).** Rejected: data-key rotation would need every credential at once.
- **SWK held server-side** (memory or Redis). Rejected: a restart would lock every session, and anything server-side is reachable by A3.
- **Key Management Service (Scaleway Key Manager) for every unwrap.** Deferred. It adds an external call on every login and doesn't change A3 or A4 (the app holds the KMS credential). Could replace §3 later for an audit trail on secret use.
- **Deriving the KEK from the bcrypt hash.** Rejected: bcrypt is the login verifier, stored in the DB.
